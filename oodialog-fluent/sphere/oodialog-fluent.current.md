# ooDialog Fluent Controls: current qualification

Architecture: Tom Dyer. Code: ChatGPT (GPT-6). Updated 2026-11-15.

Project lane: `oodialog_fluent_controls` (Rasen Falcon). Source: `animatedads/oorexx`, branch `feature/oodialog-fluent-controls-20261115`, path `oodialog-fluent/`.

## What exists

- 83 named Windows UI controls, layouts and system features in one machine-checked catalogue. `availability=stable` means Microsoft WinUI API availability **only**.
- Native-independent C++17 model preserving resource ID plus occurrence UID, strongly checked control properties and handlers, deterministic event queue and removal.
- C ABI `oodf_*` for the native ooRexx bridge and Windows XAML Island DLL. Buffer-too-small does not drop an event. **Native event callbacks and Rexx event polling are thread-safe at the ABI session boundary**, including the pending retry envelope; a 300-event cross-thread test runs on Windows/Ubuntu.
- Executable test suite; `sh tests/run_tests.sh`. CMake/CTest and Ubuntu/Windows CI workflow candidates.
- Windows x64 C++/WinRT native provider and native ooRexx package DLL **BUILD_PASS** (GitHub CI run 43724613822); four real control creation paths.
- **Unqualified ooDialog bridge candidate**: `windows/OodFluentRexx.cpp` exports the ooRexx `RexxGetPackage` routine table from the provider DLL; `rexx/OodFluent.cls` provides `.OodFluentHost` and `.OodFluentControl` compatible proxies. Native functions accept ooDialog's 0x-prefixed HWND and tokenised session/occurrence identities. The **HWND-owning UI thread only enqueues events**; ooDialog's Rexx activity explicitly drains the queue into dialog methods.
- **Windows HWND runtime probe**: `windows/OodFluentSmoke.cpp` creates a real Win32 HWND and XAML island, and verifies creation, property updates, native message pump and teardown separately by control family. Empty island, `Button`, `ToggleSwitch`, `CheckBox`, `ToggleButton`, `Slider` and **the five together** pass through clean close (CI run [43761615206](https://github.com/animatedads/oorexx/actions/runs/43761615206)). `InfoBar`, `NumberBox`, `TextBox`, `ProgressBar` create/update in diagnostic mode but crash at `DesktopWindowXamlSource.Close`, exit `0xC0000005`. All four are **refused by default with `E_NOTIMPL`**; `OODF_ALLOW_UNQUALIFIED_NATIVE=1` is for isolated testing only.
- **Native crash evidence**: CI run 43724613822 contains 134,631-byte minidump and cdb symbolic call stack. Fault at `Microsoft_UI_Xaml!ComPtr<IContentIsland>::As<IContentIslandExperimental>+0x18` (null), called by `DirectUI::XamlIsland::Close+0x195` then `DesktopWindowXamlSource::Close+0x102`. Retaining controls, clearing focus and closing InfoBar first did not repair it; CI run 43725003804 additionally shows explicit unload and 40 dispatcher turns also fail. CI now requires the safe-mode runtime subset to pass and reports unsafe-control crashes separately; a green badge is **not** full runtime PASS for all 83 catalogue targets.
- **First real ooDialog process PASS**: CI run [43729428411](https://github.com/animatedads/oorexx/actions/runs/43729428411) first established SHA-256-pinned official portable ooRexx 5.2.0 ZIP loading `OodFluentWindows.dll` and `OodFluent.cls`, asynchronous `UserDialog` hosting Button and ToggleSwitch, changing properties and closing from `ok` with exit 0. Later runs supersede that initial narrow milestone with five native controls and four programmatic event types.
- **Five-control ooRexx event and repeatability qualification**: mandatory Windows CI run [43761615206](https://github.com/animatedads/oorexx/actions/runs/43761615206) repeats the real five-control `UserDialog` session **three times**, all exit=0. After binding, ooRexx changes `ToggleSwitch.IsOn`, `CheckBox.IsChecked`, `ToggleButton.IsChecked` and `Slider.Value`; native XAML queues four independent event kinds, Rexx `dispatchPending` calls four dialog instance methods. All three logs contain `REXX_SMOKE_EVENT=toggle 202 800000002 true`, `REXX_SMOKE_EVENT=check 203 800000003 true`, `REXX_SMOKE_EVENT=toggleButton 204 800000004 true`, `REXX_SMOKE_EVENT=slider 205 800000005 42.500000`, `REXX_SMOKE_EVENTS_DISPATCHED=4`, `REXX_SMOKE_END_ASYNC_RESULT=1`, `REXX_PROBE_PASS=3/3`. `endAsyncExecution` is essential: run 43729845778 demonstrated occasional ooRexx teardown AV without it. **This proves programmatic property-driven event routing, not physical user input or UIA.**
- **Crucial ooDialog threading boundary**: observed `initDialog` Rexx activity and its HWND owner have different Windows thread IDs. The WinUI island must initialize and operate on the HWND-owning thread. `windows/OodFluentRexx.cpp` now has a same-process `WH_CALLWNDPROC` synchronous broker which marshals create/set/move/remove/close and keeps XAML callbacks out of Rexx. This is **disabled by default** (`RPC_E_WRONG_THREAD`); diagnostic test requires `OODF_TEST_CROSS_THREAD_HOOK=1` until bounded cancellation, teardown/reentrancy and accessibility are qualified. Do not call this released or general-purpose.
- **Stable authored UID**: `Session::createWithUid`, `oodf_create_authored`, `oodf_win_add_authored`, and `OodfNativeCreateAuthored` maintain authored occurrence UID across backend recreation/reopen; duplicates and zero are rejected. Dynamic controls retain a noncolliding auto UID. **1307/1307** native-independent checks.

## What does not exist

- No **visual or physical input-event PASS** for the island inside a running ooDialog process; `UserDialog` lifecycle and four property-triggered native events → Rexx methods pass 3/3 in diagnostic mode. Four complex-control templates still crash this host at shutdown and are disabled.
- The real ooRexx package-loading and `UserDialog` lifecycle test is a **required CI gate**, still not released to normal application consumers because the cross-thread hook is opt-in.
- No Windows `UserDialog`, `ResDialog`, `RcDialog` runtime parity qualification.
- No claim of native control coverage, 100% migration or deployed release.

## Continuation instructions

Read `docs/WINDOWS_HOST_CONTRACT.md`, `windows/README.md` and the upstream `DialogControls.cls`/`oodialog.dll` package entry first. Continue Windows App SDK 2.6.5 native HWND control-family isolation, **never silently enable the four unsafe templates**. Prioritize UI-thread broker deadline/cancellation/reentrancy safety, physical mouse/keyboard + UIA event tests, `ResDialog`/`RcDialog`, ooRexx 5.3 compatibility and typed property codecs for list/date/color families. Keep ooRexx objects behind the C ABI, with no hand-coded Python orchestration and no changes to other lanes' files.

**Qt6 lane review REQ-00003661**: keep all Rexx proxy classes prefixed (`.OodFluent*`) and do not subclass upstream `DialogControl`; `connectEvent` is local to these proxies. Authored UID support is now implemented in the model and native APIs, but namespace collisions across renderer providers and long-lived IDs remain a parity test. Define typed complex property codecs before implementing list/date/color control families. A portable Rexx provider seam for WinUI, Qt6 and Web is under design, not a claim of Linux WinUI availability. The overlap between `oodialog_linux` and Claude's native `oodialog-qt6-v0.7` remains an owner/architecture decision; do not claim either lane merged.

Old ooDialog runs unchanged; Linux/Qt6, browser/WASM and Wire follow their own authority boundaries. The Designer may import this catalogue after its owner agrees the extension seam; preserving resource ID, UID and event names is mandatory. Experimental WinUI controls must be gated.
